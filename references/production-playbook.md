  

# 生产手册 — 真人口播网感视频制作规范

> 本文件是 `jackyshen-talking-kinetic-video` skill 的详细生产手册。
> 
> 规定内容剪辑、视觉风格、字幕动效、共享资源、本机公共引擎、渲染流程和交付标准。
> 
> 每个视频项目独立管理；公共引擎和共享资源只维护一份，直接复用 skill 自身目录。

# A. 制作目标与创作规范

## 1. 核心任务

将用户提供的真人口播视频剪辑成节奏清晰、重点突出、有网感、有活人感的口播视频。

主要工作：

1. 转写视频口播内容，提取时间码。
    
2. 根据口播稿清理水词、停顿、重复、结巴、啰嗦、口误和不适宜内容。
    
3. 对校订后的口播稿提炼重点、关键词和关键表达。
    
4. 为重点内容设计动态大字和跟读字幕。
    
5. 根据视频素材选择视觉风格、人物表现方式和画面布局。
    
6. 根据需要增加文字动画、转场、蒙版、贴纸和装饰元素。
    
7. 从共享音乐和音效资源库选择合适的素材。
    
8. 渲染、合成、切片、检查并交付成片。
    

**核心创作原则：真人和真实内容是主体，动态文字和转场特效负责强化表达。**

不要为了展示技术能力而加入无关的示意动画、信息图、关系图或装饰。视觉效果必须服务于内容表达。

## 2. 用户输入与默认行为

### 2.1 素材输入

开始工作前，检查用户提供的：

- 原始视频和音频
    
- 口播稿或字幕文件
    
- 图片、视频和其他辅助素材
    
- 音乐及音效资源
    
- 字体、品牌和视觉参考
    
- 用户指定的风格、平台、画幅和交付要求
    

如果用户已经提供口播稿，以用户稿件为基础，并与原始视频核对。

如果用户没有提供口播稿，主动转写和校订，不要等待用户补稿。

### 2.2 默认规则

|项目|默认行为|
|---|---|
|画面主体|真人口播，不擅自加入示意动画或信息图|
|默认风格|S1 综艺黄黑|
|文字效果|重点大字 + 跟读字幕|
|大字长度|原则上 3–8 个汉字|
|同屏文字|最多 3 个文字块，每块不超过 2 行|
|原片字幕|优先保留，计入同屏文字块|
|背景音乐|从共享音乐资源库选择|
|音效|从共享音效资源库选择|
|无原片字幕|生成独立字幕文件，不默认烧录|
|视频工程|使用共享引擎创建，不在项目内复制引擎|
|字体|优先使用本机共享字体及公共引擎字体|

用户指定的要求优先于默认规则。

### 2.3 需要向用户确认的情况

仅在缺失信息会实质影响结果时询问，例如：

- 必要素材缺失。
    
- 多项剪辑要求互相冲突。
    
- 输出格式或画幅要求不明确且影响制作。
    
- 用户指定的音乐、字体或素材无法找到。
    
- 需要删除或替换原片中重要内容，但用户意图不明确。
    

其他情况采用合理默认值继续执行。

## 3. 口播内容处理

### 3.1 转写与校订

没有口播稿时，标准顺序：

1. 提取原视频音频。
    
2. 进行语音识别。
    
3. 根据上下文人工校订。
    
4. 标记停顿、重复、口误和可剪辑区间。
    
5. 形成带时间码的正式口播稿。
    

**ASR 结果只是初稿，不能直接当成最终口播稿。**

重点核对：

- 数字、金额、日期
    
- 人名、地名、机构名
    
- 产品名称、专业术语
    
- 中英文混说
    
- 同音词和容易误识别的词
    
- 短句和语义不完整的片段
    

短于 1 秒、只有一两个音节的片段，不得直接认定为语气词并删除。必须重新转写或回听原片，避免误删下一句话的动词或关键内容。

### 3.2 清理内容

根据实际情况删除：

- 无意义的语气词和口头禅
    
- 不适当的气口停顿，尤其是超过 0.3 秒的无意义停顿
    
- 重复表达
    
- 结巴和重复起句
    
- 过度啰嗦的表达
    
- 明显口误
    
- 口误后又重复表达同一意思的内容
    
- 脏话、违规和敏感表达
    

注意：

- 删除内容不能改变原意。
    
- 不要为了节奏破坏语句完整性。
    
- 不要擅自改写用户观点。
    
- 不确定是否应该删除时，回听原片。
    
- 保留必要的情绪、语气和表达节奏。
    

### 3.3 重点提炼

从真实口播内容中提取重点，而不是只根据标题或选题推断。

优先提炼：

- 核心观点
    
- 关键结论
    
- 有冲击力的表达
    
- 数字和对比
    
- 重要概念
    
- 关键术语
    
- 能够独立成立的短句
    

动态大字建议 3–8 个汉字，宁可简洁，也不要为了凑字数改变原意。

英文专业术语可以保留原文，并与中文搭配呈现，不要擅自翻译掉必要的英文表达。

### 3.4 切片

- 每个切片尽量形成完整语义单元。
    
- 避免从句子中间截断。
    
- 保留必要上下文。
    
- 重要观点、故事转折和结论可以独立成段。
    
- 长视频的分段切片本身就是可复用素材，交付时应一并提供。
    

## 4. 字幕与动态文字规范

### 4.1 文字层级

一屏最多 3 个文字块，每块最多 2 行。

|层级|作用|参考字高（1080px 宽）|
|---|---|---|
|超大字|情绪句、价格、结论|130–190px|
|大字|常规重点字幕|90–125px|
|中字|补充说明|55–80px|
|小字|英文、辅助信息|30–45px|

原片自带字幕也计入文字块数量。

不要把所有层级同时堆在画面上。没有必要时，减少文字。

### 4.2 字体

- 超粗黑体适合跟读字幕和主标题。
    
- Noto Sans SC 900 是默认主字体。
    
- 思源黑体 Heavy 可作为替代。
    
- Noto Serif SC 适合衬线铜金风格。
    
- 手写毛笔或粗马克笔适合背景巨字和装饰标题。
    
- Emoji 可用于少量注意力强调。
    
- 英文辅助文字应保持可读，不要抢过中文主体。
    

实际字体文件路径和加载规则见本文件第 11 节。

### 4.3 颜色

- 一条视频原则上只锁定一个主强调色。
    
- 其他文字以白色、黑色或中性色为主。
    
- 强调色用于关键词，不要整段文字全部染色。
    
- 同一行可以混合白色和主强调色。
    
- 描边和阴影统一使用黑色或深色，不要随意引入第二个强调色。
    
- 具体颜色按所选风格规格执行。
    

### 4.4 描边与投影

**每段重点文字必须带黑色描边和轻投影。**

推荐 CSS：

```
-webkit-text-stroke: 6px #06080C;
paint-order: stroke fill;
text-shadow: 0 6px 20px rgba(0,0,0,.6);
```

描边参考范围 4–8px，根据字号和字体调整。

`paint-order: stroke fill` 是关键：描边应画在字面之下，避免覆盖笔画。

彩色文字同样需要描边。

### 4.5 文字位置

文字位置必须根据真实视频画面测量，不要凭感觉猜。

重点测量：

- 人脸和头顶位置
    
- 人物运动范围
    
- 原片字幕区域
    
- 重要背景信息
    
- 可用排字空间
    

文字位置应记录在 `direction.md`，并说明布局依据。

跟读字幕的 Y 位置可以在画面高度约 49%–80% 之间变化，不要机械固定在同一条线上。

- 大词可以上移。
    
- 叙述句可以下沉。
    
- 人脸和原字幕区域必须避让。
    
- 可以错位排布或贴边，但不能影响必要信息的辨识。
    

### 4.6 原片自带字幕

优先保留原片烧录字幕。

原因：

- 原字幕已经属于画面叙事层。
    
- 去除字幕可能破坏背景纹理、衣物和其他画面细节。
    
- 简单使用 `delogo` 或模糊覆盖可能形成明显脏块。
    

确实需要去除时，优先改构图、裁切或重新布局，而不是简单糊掉。

原片字幕保留时：

- 原字幕作为叙事层。
    
- 动态大字另找位置。
    
- 避免在相同区域重复显示内容。
    
- 同屏文字块仍然计数。
    

### 4.7 亮背景处理

如果文字位于窗户、白墙等亮背景上，可以增加柔和的暗渐变。

要求：

- 渐变没有明显硬边。
    
- 根据实际背景对比度调整透明度。
    
- 可以随文字出现和消失轻微变化。
    
- 不要为了突出文字把整幅画面压得过暗。
    

## 5. 人物画面处理

根据素材选择人物表现方式，不要求每条视频使用全部方式。

|方式|处理|适用场景|
|---|---|---|
|全身入镜|保留原始画面|开场、展示产品|
|半身/大特写|保留原始画面|人物讲述主体|
|抠像 + 模糊背景|人物抠像，背景使用同一镜头放大并高斯模糊|需要腾出空间放大字|
|抠像 + 白色描边贴纸|人物抠像，外侧增加白色描边|B-roll 中保留人物|
|圆形小窗|人物使用圆形 alpha 遮罩|B-roll 为主、偶尔露脸|
|纯 B-roll|人物不出镜|产品特写、场景交代|

人物位置与文字位置应互相配合。

例如，人物位于右下角时，文字可以在左侧或顶部；人物位于左上角时，文字可以在右侧或下方。

真人大脸是主体时，不要擅自增加示意动画、信息图或关系图。

## 6. 动效与转场

### 6.1 基础动效设备

公共引擎应支持以下基础动效：

|设备|表现|适用场景|
|---|---|---|
|`drop`|从上方落入并带轻微模糊|短促断言|
|`wipe`|从左侧擦入|普通陈述|
|`slam`|缩放砸入后回正|转折、结论|
|`slideL`|从左侧滑入并带拖尾|过程描述|
|`type`|逐字出现|英文术语、概念句|
|`split`|整句上下裂开，中间出现第二句|前后反转、结论|

基础参数可参考：

- 入场约 420ms。
    
- 出场约 320ms。
    
- 出场通常采用上抽、轻微缩小、模糊和淡出。
    
- `type` 逐字间隔可参考 35ms。
    

具体时间根据文字长度、节奏和组时长调整。

### 6.2 叠印转场

推荐使用文字叠印，而不是每句之间完全清空画面。

做法：

- 下一组文字提前进入。
    
- 上一句在原位置缩小、淡出或被覆盖。
    
- 两组短暂同时存在。
    
- 组间重叠参考 0.3–0.45 秒。
    
- 避免旧句残留和新句提前出现。
    

不要为了叠印破坏阅读节奏。

### 6.3 其他转场

根据内容需要选择：

- 圆形蒙版
    
- 长方形蒙版
    
- 整个画面轻微晃动
    
- 淡入淡出
    
- 上下或左右分裂
    
- 局部放大或缩小
    
- 人物小窗与背景切换
    

转场不是必需品。许多视频只靠文字叠印、人物镜头变化和字幕节奏就足够。

### 6.4 圆形蒙版

圆形蒙版可以用于凸显口播者的大头。

通用原则：

- 圆心必须根据当前视频的人脸位置测量。
    
- 圆孔半径必须根据当前视频头部尺寸确定。
    
- 不得直接复制其他视频的圆心和半径。
    
- 最小圆孔应保持主播完整头部可见，不要收缩至全黑。
    
- 一次收缩再扩展的章节转场可参考 2 秒。
    
- 转场音效应与圆孔收至最小的关键帧同步。
    
- 文字层应位于蒙版之上，避免大字被意外裁切。
    

技术实现见第 17.4 节。

## 7. 七套视觉风格

七套风格是通用视觉体系。用户指定风格时优先遵循；未指定时默认 S1。

选择风格后，应整体采用该风格的字体、布局、描边、配色、人物处理和动效，不要随意混搭。

画面中禁止显示内部系列编号或风格代号。

### 7.1 风格选型表

|编号|风格|一句话特征|主色|默认|
|---|---|---|---|---|
|S1|综艺黄黑|底部跟读字幕 + 人脸后方巨幅手写笔刷字|金黄 `#FEBD0D` / 橙|是|
|S2|衬线铜金|宋体铜金渐变标题 + 人物抠像缩至右下角|铜金 `#E1A880`||
|S3|薄荷绿双语|绿色引号标题 + 中英双语 + Emoji 贴纸|薄荷绿 `#79F0BA`||
|S4|双层错位|顶部两层标题互相压 + 人物白色描边贴纸|柠檬黄 `#FAF07B`||
|S5|便利贴叠压|白底便利贴标题 + 大小字叠压 + 手机相机 UI|明黄 `#F9C900` + 正红 `#F80309`||
|S6|木纹促销|木纹条标题 + 绿色标签 + 圆形人物小窗|荧光绿 `#27FAB3`||
|S7|粉黄撞色|粉黄撞色标题 + 圆形人物小窗 + 米色画框|粉色 `#FDABBB`||

### 7.2 S1 综艺黄黑（默认）

**字体**

- 主字幕：Noto Sans SC 900 超粗黑体。
    
- 背景巨字：手写毛笔体。
    

**布局**

- L1 顶部钩子条：Y 4%–19%，两行。
    
    - 第一行白字。
        
    - 第二行橙色或黄色。
        
    - 均带黑描边。
        
- L2 底部跟读字幕：Y 59%–80%，1–2 行，字高 100–190px。
    
    - 白字行和橙黄行交替。
        
- L3 背景巨字：Y 15%–38%，横跨画面宽度约 8%–95%。
    
    - 手写笔刷字。
        
    - 金黄 `#FEBD0D`。
        
    - 黑色描边。
        
    - 位于人物头部后方。
        

**描边**

- 黑描边 6–10px。
    
- 适量投影。
    

**人物**

- 真人半身或大特写。
    
- 不抠像。
    

**动效**

- 标题条静止。
    
- 字幕使用上方压入、旧句缩淡。
    
- 背景巨字使用盖章式砸入，参考 scale 1.2 → 1。
    

### 7.3 S2 衬线铜金

**字体**

- 主标题：宋体/明朝体，例如 Noto Serif SC。
    
- 跟读字幕：超粗黑体。
    

**布局**

- L1 顶部铜金渐变大标题，Y 5%–45%，可使用多行。
    
- L2 底部橙黄跟读字幕，Y 55%–78%。
    

**描边**

- 铜金渐变填充。
    
- 黑描边约 6px。
    
- 下投影。
    

**人物**

- 抠像。
    
- 背景使用同一镜头放大并高斯模糊。
    
- 人物抠像放在右下角，参考 X 45%–95%、Y 52%–100%。
    

**动效**

- 标题逐行落下，使用 stagger。
    
- 跟读字幕使用压入效果。
    

**适用**

- 专业知识
    
- 鉴定
    
- 对比
    
- 有质感的知识表达
    

### 7.4 S3 薄荷绿双语

**字体**

- 超粗黑体 900。
    
- 主标题使用引号块。
    

**布局**

- 主标题：Y 54%–66%，薄荷绿。
    
- 第二行白色大字：Y 66%–76%，与第一行错位。
    
- 中文和英文可以组合：
    
    - 中文约 Y 64%–70%。
        
    - 英文约 Y 70%–74%。
        

**配色**

- 薄荷绿 `#79F0BA`
    
- 白色
    
- 灰色英文辅助文字
    

**装饰**

- Emoji 贴纸，例如 👍。
    
- 弹入并轻微旋转。
    
- 人物底部可增加黑色渐变带，参考 Y 72%–100%。
    

**适用**

- 涉外内容
    
- 英文术语较多
    
- 中英混合表达
    

### 7.5 S4 双层错位

**字体**

- 超粗黑体。
    
- 手写体。
    
- 两层叠印。
    

**布局**

- 顶部两层标题互相压：
    
    - 白色手写层：Y 8%–16%。
        
    - 黄色粗体层：Y 14%–22%。
        
    - 两层垂直错位约 6%。
        
- 中英双语字幕：Y 55%–66%。
    

**人物**

- 白色描边人物贴纸。
    
- 描边约 8–12px。
    
- 位置参考 X 5%–40%、Y 58%–100%。
    

**文字**

- 可以右对齐并贴近右边缘。
    
- 允许少量文字被画面边缘裁切，但不能影响关键语义。
    

**适用**

- 产品视频
    
- 门店视频
    
- 以 B-roll 为主的画面
    

### 7.6 S5 便利贴叠压

**字体**

- 超粗黑体。
    

**布局**

- L1 顶部白色矩形贴纸，参考 Y 0%–5%，使用黑字标题。
    
- 下方白字黑描边副题，参考 Y 5%–17%。
    
- L2 底部大小字叠压：
    
    - 小字 Y 52%–58%。
        
    - 大字 Y 56%–66%。
        

**配色**

- 明黄 `#F9C900`。
    
- 正红 `#F80309` 用于强调词。
    

**装饰**

- 手机相机 UI：
    
    - 取景框。
        
    - 红色录制按钮。
        
    - 时间码。
        
- 四周可以增加暗角。
    

**适用**

- 有冲突的故事。
    
- 反转。
    
- 悬念开头。
    

### 7.7 S6 木纹促销

**字体**

- 超粗黑体。
    

**布局**

**人物**

**字体**

**布局**

    - 白色黑描边说明行，参考 Y 17%–24%，可带引号。

### 7.9 风格选择决策

|素材或话题特征|推荐风格|
|---|---|
|真人大脸口播、顶部有安全带|S1|
|专业知识、鉴定、对比|S2|
|中英混说、英文术语多|S3|
|产品 B-roll 为主、人物少量出镜|S4 或 S6|

|促销、活动、周年庆|S6|

### 7.10 七套风格共同底线

- 黑色描边约 4–8px，按字体和字号调整。
    
- 每套风格只锁一个主强调色。
    
- 字幕 Y 位置可以在 49%–80% 之间浮动。
    
- 价格和结论句可以独占一屏。
    
- 人物景别根据内容变化。
    
- 文字可以错位、贴边，但要保证关键内容可读。
    
- 同屏最多 3 个文字块，每块不超过 2 行。
    

## 8. 标准制作流程

每个阶段完成后先检查结果，再进入下一阶段。

### 阶段一：素材分析

1. 检查原始视频、音频和辅助素材。
    
2. 确认视频时长、分辨率、帧率和画幅。
    
3. 检查是否有原片字幕。
    
4. 分析人物位置、背景亮度和画面变化。
    
5. 检查音乐、音效和字体资源。
    
6. 确认用户要求的输出形式。
    

产出：素材分析记录。

### 阶段二：转写与校订

1. 提取音频。
    
2. 使用 ASR 转写。
    
3. 人工校订。
    
4. 核对数字、专名、英文和专业术语。
    
5. 标记停顿、重复、口误和剪辑区间。
    

产出：`口播稿.md`

### 阶段三：内容剪辑与切段

1. 清理无效表达。
    
2. 保留完整语义。
    
3. 确定切片边界。
    
4. 提炼每段核心观点。
    
5. 为重点句和关键词标记时间码。
    

产出：

- 校订口播稿
    
- 分段切片方案
    
- `打点表.md`
    

### 阶段四：视觉设计

1. 分析人物及原字幕位置。
    
2. 测量可用排字区域。
    
3. 选择视觉风格。
    
4. 确定字体、字号、颜色和位置。
    
5. 提炼动态大字。
    
6. 规划入场、出场和转场。
    
7. 确定音乐和音效。
    

产出：`direction.md`

### 阶段五：时间轴设计

将口播段落、文字内容、动画、蒙版和音效转换为机器可执行的时间轴。

产出：`timeline.json`

### 阶段六：构建与渲染

1. 检查时间轴数据。
    
2. 检查文字长度、字号、宽度和位置。
    
3. 生成文字及蒙版图层。
    
4. 按时间轴逐帧渲染。
    
5. 使用 FFmpeg 合成视频和音频。
    
6. 根据需要生成分段切片。
    

### 阶段七：预览和质量检查

1. 打开引擎预览模式。
    
2. 检查整体字幕布局。
    
3. 检查每组中点。
    
4. 检查组间空隙帧。
    
5. 检查动效中间帧。
    
6. 检查蒙版转场。
    
7. 检查音画同步。
    
8. 检查成片时长、分辨率、帧数和响度。
    

### 阶段八：交付

交付最终成片、字幕、口播稿、时间轴、切片及必要的预览。

同时将预览推进 Codex 右侧边栏，具体方式见第 18 节。

## 9. 最终交付物

通常包括：

1. 最终口播动效视频。
    
2. 纯人声版。
    
3. 分段切片。
    
4. 校订后的口播稿。
    
5. 剪辑打点表。
    
6. 时间轴 JSON。
    
7. 独立字幕文件（如需要）。
    
8. 预览入口和必要说明。
    

交付说明应明确：

- 哪个文件是最终成片。
    
- 哪个文件是预览。
    
- 哪些文件是分段切片。
    
- 是否存在尚未完成的检查或限制。
    

最终判断标准：

**内容准确、表达清楚、画面舒服、节奏自然、文件可靠。技术效果不是交付目标本身。**

公共引擎 CSS 别名：

### 11.5 字体加载规范

必须保证：

- 字体文件实际存在。
    
- `@font-face` 声明正确。
    
- CSS 使用的字体别名与声明一致。
    
- `document.fonts.load()` 使用相同的字体别名。
    
- 等待字体真正加载完成后再渲染。
    

示例：

```
@font-face {
  font-family: "brush";
  src: url("./assets/brush.ttf") format("truetype");
  font-weight: 400;
}
```

```
await document.fonts.load('400 112px "brush"');
await document.fonts.ready;
```

注意：

`brush.ttf` 是文件名，`brush` 是 CSS 别名，`ZiYuQingMeiYingBi` 是字体真实名称。三者不能混淆。

更换字体时，必须同时检查字体声明和实际加载调用。

# C. Agent 执行与技术实现

## 13. Agent 工作规范

### 13.1 开始前检查

开始工作前：

1. 阅读全局 `~/.codex/AGENTS.md`。
    
2. 读取本 skill 的 `SKILL.md` 和本生产手册。
    
3. 检查 skill 内的共享音乐、音效和字体资源路径。
    
4. 检查 skill 内的公共引擎。
    
5. 检查现有项目文件。
    
6. 确认当前项目的渲染方式和依赖。
    

不要未经检查就重写工程。

### 13.2 内容和技术分离

建议将项目拆分为：

|层|职责|
|---|---|
|内容层|口播稿、重点、切片|
|视觉层|字体、配色、布局和风格|
|时间轴层|时间、文字、位置、动效|
|渲染层|字体、布局、动画和蒙版|
|合成层|视频、音频和透明图层|
|QA 层|自动检查和人工抽帧|

能通过修改 `timeline.json` 解决的问题，不要修改渲染引擎。

能通过复用现有动效解决的问题，不要重复实现。

### 13.3 不得臆造

- 不得虚构视频中没有出现的口播内容。
    
- 不得虚构素材库中的音乐、音效和字体。
    
- 不得把低置信度 ASR 结果当作事实。
    
- 不得未经确认改变用户原意。
    
- 不得将其他视频的专属配色、坐标和动效直接套用。
    
- 不得虚构本机文件路径。
    

### 13.4 技术变更

- 优先使用现有技术栈。
    
- 新增第三方库前，先判断现有实现是否足够。
    
- 考虑离线渲染和本地部署。
    
- 不要为简单动画引入复杂运行时。
    
- 新功能应尽可能做成可复用组件。
    
- 修改公共引擎后必须进行回归检查。

## 16. 转写、版面与音频技术规范

### 16.1 语音转写

推荐使用 whisper.cpp 或其他可用 ASR 工具。

本机常用配置：

```
可执行文件：/opt/homebrew/bin/whisper-cli
模型：~/.cache/whisper/ggml-medium.bin
```

典型命令：

```
ffmpeg -i in.mov -vn -ac 1 -ar 16000 audio.wav

whisper-cli \
  -m ~/.cache/whisper/ggml-medium.bin \
  -l zh \
  -f audio.wav \
  -osrt -ojf -olrc \
  -of out \
  -ml 22 \
  -sow \
  --prompt "<领域词、专名、产品名>"
```

参数说明：

- `-ml 22`：限制每段长度。
    
- `-sow`：按词切分。
    
- `--prompt`：提供领域词、专名和产品名，改善识别。
    

模型路径必须检查实际存在，不要假设 Homebrew 安装目录中的测试模型就是生产模型。

### 16.2 画面测量

使用 Python、OpenCV 或其他图像工具分析视频帧。

可以使用以下方法作为初始测量：

**检测原片字幕带：**

统计近白像素的行数，寻找字幕密集区。

```
for y in range(1100, 1920, 4):
    white = (
        (a[y, :, 0] > 215) &
        (a[y, :, 1] > 215) &
        (a[y, :, 2] > 215)
    ).sum()
```

**检测人脸头顶：**

统计暗像素或肤色像素的分布，寻找头顶边界。

实际检测方式应根据人物、衣服、背景和光线选择。

**测量原则：**

- 对动态人物采样多个时间点。
    
- 取最不利的遮挡边界。
    
- 不要只依据单帧确定文字位置。
    
- 把测量结果记录到 `direction.md`。
    
- 每条视频重新测量，不复制其他视频的坐标。
    

### 16.3 音频响度

参考目标：

- 综合响度：约 -16 至 -20 LUFS。
    
- True Peak：不高于 -1.5 dBTP。
    

使用 FFmpeg `loudnorm`：

第一遍检测：

```
ffmpeg -i src.mov \
  -af "loudnorm=I=-16.5:TP=-1.5:LRA=11:print_format=json" \
  -f null -
```

第二遍根据检测结果使用 measured 参数进行线性归一化。

不要未经检测就机械套用固定参数。

### 16.4 背景音乐

- 人声是主要信息。
    
- 音乐不能遮盖人声。
    
- 根据内容情绪和节奏调整音量。
    
- 需要时在开头和结尾淡入淡出。
    
- 不要为了形式给每条视频强行添加音乐。
    

## 17. 公共引擎技术实现规范

### 17.1 渲染架构

默认采用：

**浏览器渲染透明文字层 → FFmpeg 合成回原视频。**

不要在浏览器里播放视频并逐帧 seek 截图来代替专业合成流程。

原因：

- 浏览器不需要 seek 视频。
    
- 不需要处理浏览器视频解码卡顿。
    
- 文字层可以独立检查。
    
- 中间帧可以逐张 QA。
    
- 出错后只重跑对应区间。
    
- 支持断点续跑。
    

典型合成：

```
ffmpeg \
  -framerate 30 -i overlay/frame-%06d.png \
  -i cut_raw.mp4 \
  -i audio.mix.mkv \
  -filter_complex \
  "[1:v][0:v]overlay=0:0:format=auto,format=yuv420p[v]" \
  -map "[v]" \
  -map 2:a \
  -c:v libx264 \
  -crf 18 \
  output.mp4
```

实际项目应根据音轨、画幅和时长调整。

### 17.2 逐帧渲染

- 时间轴与视频帧率一致。
    
- 使用明确的时间基准。
    
- 帧文件有稳定命名。
    
- 支持按时间段续跑。
    
- 已存在的帧可以跳过，但必须检查文件完整性。
    
- 文字层和蒙版层必须使用相同时间基准。
    

### 17.3 CSS 动画静默失败

CSS 动画可能没有明显报错，却不显示或显示错误。

|现象|常见原因|处理|
|---|---|---|
|前几帧文字消失|可变字体尚未触发加载，`document.fonts.ready` 提前完成|显式 `document.fonts.load()` 并等待布局|
|文字跑出画面|多个文字块塞入居中容器，内容过高导致负 Y|每组绝对定位，使用固定行槽|
|字重或字形错误|字体声明或字体栈不完整|检查 `@font-face` 和 computed font|
|强调色失效|CSS 选择器和实际 DOM 不匹配|检查选择器|
|英文空格消失|逐字拆成 inline-block 后空白塌陷|`.ch{white-space:pre}`|

调试时重点检查：

```
getComputedStyle(element)
element.getBoundingClientRect()
```

渲染前应检查：

- 字体是否加载。
    
- 元素是否在画面内。
    
- 元素宽度是否正确。
    
- 字重和字体是否正确。
    
- 空格是否保留。
    

### 17.4 Split 上下裂开动效

效果：

1. 第一句完整出现。
    
2. 文字从水平中线裂成上下两半。
    
3. 两半分别向上下移动，保留可见内容。
    
4. 中间形成空隙。
    
5. 第二句以不同颜色和字体出现。
    
6. 两句话一起淡出。
    

**实现原则：**

不需要为了这个效果引入复杂动画库。两半对称移动，第二句位置可以静态计算。

CSS：

```
.item.split .splitwrap {
  display: inline-grid;
}

.item.split .half {
  grid-area: 1 / 1;
}

.item.split .half.top .tw {
  clip-path: inset(0 0 50% 0);
}

.item.split .half.bot .tw {
  clip-path: inset(50% 0 0 0);
}
```

DOM：

```
.item.main.split
  └ .splitwrap
      ├ .half.top > .tw
      └ .half.bot > .tw
```

注意：

- 两个文字副本必须叠在同一 grid 单元。
    
- 不要只用 `position:absolute`，否则容器宽度可能塌成 0。
    
- 出场缩放必须作用在 `.splitwrap`，不能作用在 `.tw`。
    
- `split` 主句必须是单行。
    
- `split` 的第二句使用 `role:"crack"`。
    
- `crack` 应使用手写字体 `brush`。
    
- 手写体描边约 4px，避免笔画被吃掉。
    
- `split.gap` 必须足够容纳第二句。
    
- build 阶段必须校验主句、第二句的尺寸、字数和垂直关系。
    

时间轴示例：

```
{
  "id": "g01",
  "y": 1300,
  "t0": 12.0,
  "t1": 16.0,
  "items": [
    {
      "id": "g01-main",
      "role": "main",
      "text": "花几个月",
      "size": 118,
      "device": "split",
      "t0": 12.0,
      "t1": 16.0,
      "split": {
        "at": 1.0,
        "gap": 76,
        "dur": 0.8
      }
    },
    {
      "id": "g01-crack",
      "role": "crack",
      "text": "几分钟",
      "size": 112,
      "device": "fade",
      "t0": 13.8,
      "t1": 16.0
    }
  ]
}
```

参数确定顺序：

1. 先确定整组时长。
    
2. 再确定 `split.at` 和 `split.dur`。
    
3. 给第二句留出足够可见时间。
    
4. 最后确定 `gap` 和第二句字号。
    

不要只看静态帧，必须检查裂开过程和第二句实际可见时长。

### 17.5 圆形蒙版

默认由浏览器文字层渲染蒙版 PNG。

**实现原则：**

- 黑色整屏图层。
    
- 使用径向渐变挖出透明圆孔。
    
- 蒙版压在底片画面之上、文字层之下。
    
- 文字在蒙版上方，保证始终可读。
    
- 文字和蒙版由同一次渲染循环生成，保证严格同帧对齐。
    

CSS：

```
#fx {
  position: absolute;
  left: 0;
  top: 0;
  width: 1080px;
  height: 1920px;
  pointer-events: none;
  z-index: 10;
}

#band {
  z-index: 20;
}
```

关键帧插值：

```
var RMAX = 2400;

function fxEase(p, kind) {
  if (kind === "inout") {
    return p < 0.5
      ? 2 * p * p
      : 1 - Math.pow(-2 * p + 2, 2) / 2;
  }

  if (kind === "in") {
    return p * p;
  }

  return 1 - Math.pow(1 - p, 2);
}

function fxRadius(f, t) {
  var K = f.k || [];
  var n = K.length;

  if (!n) return RMAX;
  if (t <= K[0].t) return K[0].r;
  if (t >= K[n - 1].t) return K[n - 1].r;

  for (var i = 0; i < n - 1; i++) {
    if (t >= K[i].t && t <= K[i + 1].t) {
      var span = Math.max(0.001, K[i + 1].t - K[i].t);
      var p = fxEase(
        (t - K[i].t) / span,
        K[i].ease || "out"
      );

      return K[i].r + (K[i + 1].r - K[i].r) * p;
    }
  }

  return RMAX;
}
```

径向渐变：

```
var g =
  "radial-gradient(circle at " +
  f.cx + "% " + f.cy + "%, " +
  "rgba(0,0,0,0) 0px, " +
  "rgba(0,0,0,0) " + r.toFixed(1) + "px, " +
  "#000 " + (r + 1).toFixed(1) + "px)";

o.el.style.webkitMaskImage = g;
o.el.style.maskImage = g;
```

注意：

- `mask-image` 和 `-webkit-mask-image` 都要设置。
    
- `RMAX` 必须大于画面对角线，确保全开时没有黑边。
    
- 圆心和半径每条视频重新测量。
    
- 最小圆孔是主播完整头部大小，不是全黑。
    
- 章节转场参考 2 秒：收拢、短暂停留、扩展。
    
- 音效落在圆孔最小帧。
    

`timeline.json` 中的 `fx` 是顶层数组，与 `groups` 平级。

示例：

```
{
  "fx": [
    {
      "id": "fx1",
      "mode": "keys",
      "t0": 0.0,
      "t1": 1.3,
      "cx": 50,
      "cy": 52,
      "k": [
        {"t": 0.0, "r": 430, "ease": "out"},
        {"t": 1.3, "r": 2400, "ease": "out"}
      ]
    }
  ]
}
```

以上坐标和半径仅为数据格式示例，不能直接作为其他视频的默认参数。

### 17.6 GSAP 与动画库选型

公共引擎目前以手写 CSS/JavaScript 动画为默认方案。

不需要为了普通文字动效、叠印或上下裂开而引入 GSAP。

只有当需要元素之间存在无法静态计算的运行时交互、复杂编排或尺寸关系时，才重新评估动画库。

选择第三方库时：

- 优先考虑离线运行。
    
- 不依赖 CDN。
    
- 评估新增依赖和维护成本。
    
- 进行性能对比。
    
- 对公共引擎做回归测试。
    

不要仅因为某个效果可以用第三方库实现，就引入新的依赖。

### 17.7 FFmpeg 合成

默认合成流程：

1. 原视频作为底片。
    
2. 透明文字 PNG 序列作为覆盖层。
    
3. 需要时加入蒙版图层。
    
4. 加入处理后音频。
    
5. 合成最终视频。
    
6. 根据时间轴切片。
    

如果蒙版和文字层由同一渲染循环输出，必须确保使用相同的 `tl.time(t)`。

## 18. 预览模式与 Codex 交付

### 18.1 预览模式

公共引擎支持：

```
node "<skill-dir>/engine/preview_server.mjs" --project "<项目绝对路径>"
```

服务打印：

```
http://127.0.0.1:8787/index.html?preview=1&edit=1
```

预览模式用途：

- 检查文字布局。
    
- 检查动效。
    
- 检查时间轴。
    
- 检查圆形蒙版转场。
    
- 不需要等待整条视频重新渲染。
    

预览控件：

|控件|功能|
|---|---|
|播放/暂停|控制预览|
|时间码|显示当前时间|
|时间轴|拖动定位|
|蓝色标记|每组大字起点|
|黄色标记|圆形蒙版转场|
|空格|播放/暂停|
|左右方向键|单帧移动|
|Shift + 左右|移动 1 秒|
|上下方向键|上一组/下一组大字|
|Home/End|首尾定位|

预览画面源：

- 自动使用 `renders/` 中的纯人声版。
    
- 不需要另外复制一份中间视频。
    
- 默认保留归一化人声。
    
- `?mute=1` 可以关闭声音。
    
- `?src=/renders/...` 可以临时指定项目内画面源。
    

预览用途是检查动效、布局和蒙版，不是检查最终混音。

需要听完整混音时，直接打开最终口播动效版。

### 18.2 预览模式与生产路径隔离

预览代码只有在 URL 参数包含 `preview` 时执行。

`<video>` 通过 JavaScript 动态注入，非预览模式下不改变生产渲染 DOM。

因此：

- 预览功能不能影响生产渲染。
    
- 修改预览代码后应回归检查生产输出。
    
- `timeline.json` 不应被预览功能自动修改。
    

### 18.3 纯人声版必须先于 build

`build.mjs --project <项目>` 会扫描该项目的 `renders/`，寻找纯人声版并将路径写入项目编译产物 `timeline.js` 的 `meta.previewSrc`。

因此生产顺序必须是：

1. 生成纯人声版。
    
2. 执行 `node "<skill-dir>/engine/build.mjs" --project "<项目绝对路径>"`。
    
3. 执行逐帧渲染。
    
4. 合成最终视频。
    

如果先 build，编译时找不到纯人声版，预览路径可能无法写入。

### 18.4 推进 Codex 右侧边栏

每个项目完成后，主动将预览推进 Codex 右侧边栏。

使用 `open_in_codex`：

```
open_in_codex({
  target: {
    type: "browser",
    url: "http://127.0.0.1:8787/index.html?preview=1&edit=1"

```

注意：

1. 先启动共享预览服务，再打开它打印的 HTTP 地址。
2. browser target 不要传 `placement`。
    
3. 返回 `queued` 属于正常结果。
    
4. 不要用系统 `open` 命令代替 Codex 侧栏预览。
    
5. 主动给用户一个可点击的 `preview` 链接。
6. 回复用户时说明这是动效预览，最终成片仍然是 `renders/` 中的 MP4。

### 18.6 预览编辑器（改文字，不用再开剪映）

预览模式下点工具条上的 **✎**（或按 `E`）进入编辑：

|能做的|怎么做|
|---|---|
|选中文字块|直接点屏幕上那个字块（只有看得见的字块才响应）|
|看动效标签|右侧面板顶部显示该字块用的动效（drop/wipe/slam/slideL/type/split）|
|改文字|面板里的文本框，`*字*` = 高亮该字|
|加高亮|选中文本框里的字 → 点「高亮选中」|
|改字号|面板里的字号输入框|
|改位置|拖动字块（**只动被拖的那一行**，大字和下面的小字各自独立）|
|改大小|拖动字块右下角的小方块|
|引用到对话|点「引用到对话」，把这一组的文字/字号/位置/动效/时间码复制到剪贴板，粘到对话里继续改|
|保存|点「保存并重建」→ 写回 `timeline.json` → 自动跑 `build.mjs`|

- 编辑器只改 `timeline.json`，不动 `index.html`。
- 每次保存留一份 `.bak`。
- **两行字是各自独立的**：大字上移不会带着小字走（小字的基准位置由大字字号决定，但拖动量记在各自身上）。
- 播放头是**红色**的（`#FF3B30`）。

### 18.7 按段删除模式（删掉说错的那一句）

用途：同一句话说了两遍、中间有一句废话、或者整段不想要 —— 在预览里直接删掉**这一句**，不用再开剪映。

打开方式：预览模式下点工具条上的 **段** 按钮。

- 时间轴上会出现**蓝色的段块**：两条蓝色分割线之间 = 一句话 / 一个短语 = 一个删除单位。
- **点某个段块** → 这一段被选中（变黄），底部条显示它的文字和时间码。
- 点「删掉这一段」（或按 `Delete`）→ 这一段立刻消失，后面的字幕和画面整体前移，总时长变短。
- 「撤销」撤回 · 「引用」把这一段的文字/时间/动效用复制到剪贴板（粘到对话里继续改）·「保存」写 `deletions.json` ·「重建」后台跑完整流水线。
- 文字块编辑（工具条上的 **✎**，或按 `E`）不受影响：点画面上的字块改文字/字号/位置/高亮。

**为什么不做逐字粒度**（2026-11-03 试过，回退了）：
- 几百个字要在时间轴上实时重绘，浏览器卡；
- 删除边界落在字中间，音频容易切出咔哒；
- 一句话/一个短语本来就是口播的自然单位，够用，也不容易误删。

#### 交互细节（2026-11-03 用户实测后定的）

|点|做法|
|---|---|
|删除的视觉反馈|时间轴上留一道**红色斜纹切痕**（`#pvcuts`），宽度就是被删掉的那一截；底部提示行再列一个红色标签「✕ 某段 3.0s」|
|保存 / 重建|合成**一个**按钮「保存并重建」——点一次就存清单 + 重出成片。分开两个按钮纯属啰嗦|
|撤销|只撤「最近一次删除」，**不管删没删过都只是内存里的待删清单**；撤销后会自动写回 `deletions.json`，不会和磁盘上的旧清单打架。没有可撤时按钮是灰的|
|引用|复制到剪贴板 + 屏幕中下方弹一条 toast「已复制引用 · 粘贴到对话框里就能继续改」。网页没法直接往 Codex 对话框里写，只能走剪贴板|
|播放头|红色、比蓝色段块高（34px vs 13px），并且带一个三角头。拖播放头不会被误判成点段|
|点段 vs 拖播放头|**段模式下 mousedown 不再 seek**：点段只是选段（选完把播放头放到该段起点），位移 >4px 才算擦洗；普通模式保留「按一下就跳」。播放头再也不会抢走点击|
|重建期间|**锁住整个编辑界面**（`body.locked`），弹一个模态框显示实时日志。理由：后台正在按 `cuts.json` 剪片子，你这时再改删除清单，两边就会打架|

#### 数据从哪来

|文件|谁生成|作用|
|---|---|---|
|`cuts.json`|`plan.py`（基线）→ `apply_deletions.py`（扣掉删除后）|切片计划 + src↔out 映射 + 每组对应的行（`gid`）|
|`timeline.json`|`mktimeline.py`（基线）→ `apply_deletions.py`（扣掉删除后）|时间轴|
|`deletions.json`|预览编辑器|待删的段（**原片时间**区间）|
|`deletions.applied.json`|`apply_deletions.py`|已经落地过的删除（重新跑 plan.py 也要继续生效）|

删一整段时，取这一组所有行（`gid` 相同的 rows）里 `src0` 的最小值到 `src1` 的最大值作为原片区间 —— 组内的气口一并删掉，这是想要的效果。

> ⚠️ **`plan.py` 必须写 `gid` 和 `groups`，否则「删掉这一段」会静默失灵**（2026-11-05 实测）。
> - 每行 row 加一个 `gid`：该行属于第几组（**0 基**的组号）；片头/组间气口/片尾这些不属于任何组的行写 `-1`。
> - `cuts.json` 顶层加一个 `groups`：`[{"i": 0, "out0": …, "out1": …}, …]`，顺序就是组序。
>
> `gid` 缺了的话，`segmode.js` 的 `groupRange()` 找不到这一组对应的行，会直接 `return` —— 点了「删掉这一段」
> 什么都不发生，也不报错。`groups` 缺了的话，`apply_deletions.py` 重建出来的分组是空的，字幕/切片会整体错位。
>
> **每集开工前先自检这两条**：
> ```python
> json.load(open("cuts.json"))["rows"][3]["gid"]          # 应为整数
> len(json.load(open("cuts.json"))["groups"]) == 32       # 应等于组数
> ```

#### 时间映射的语义（预览和重建必须一模一样）

删掉一段视频 = 这段消失，后面整体提前：

- 完全在删除点之后的组：`t0/t1` 一起提前 Δ。
- **横跨删除点的组**：`t0` 不动，`t1` 提前 Δ（动画不跳帧，尾巴被剪短）。
- 完全落在删除区间里的组：塌成 0 长度 → 标记 `dead` / `deadNow`，**保留在列表里**（下游脚本按序号对齐，直接删掉会导致音效落错组），渲染时跳过。
- 删除区间按**帧**算（不是按秒），浏览器和 `apply_deletions.py` 必须逐帧一致。
- 舍入统一用 `Math.round` 语义（Python 用 `int(math.floor(x+0.5))`，不要用 Python 的 `round()`）。

#### 重建的顺序（不能改）

```
plan.py          → 基线 cuts.json
mktimeline.py    → 基线 timeline.json
apply_deletions.py → 扣掉删除 → cuts.json + timeline.json + cut_fast.filter → 立刻清空 deletions.json
切原片 → 纯人声版 → build.mjs → 逐帧文字层 → 配乐音效 → 合成
```

- `apply_deletions.py` 必须在 `mktimeline.py` **之后**跑（它要同时改两份文件）。
- 扣完就清空 `deletions.json`（已落地的记在 `deletions.applied.json`），否则 `build.mjs` 会把「待删」再编进 `timeline.js`，预览会在已经剪好的时间轴上**再删一次**，字幕整体再多前移一段 → 错位。
- 快剪路径：从 `cut_base.mp4`（基线切片，只切一次）再切一刀，`veryfast` 十几秒；
  要最高画质用 `QUALITY=1 ./rebuild.sh` 从原片重切。

#### 七个必须守住的坑（2026-11-03 用户实测踩到）

1. **「字幕删了、画面没删」= 时钟不能反推**
   - 预览时钟必须**由视频驱动**：`clock = vid.currentTime - removedBefore(vid.currentTime)`（纯函数，不累加）。
   - 撞到被删区间就 seek 一次跳过去；**不要用墙钟累加再回头纠正** —— 那样会反复 seek，
     听感就是「滋啦滋啦」，而且一次 seek 失败就永久错位。
   - 能不在正常播放时 seek 就别 seek：没有删除时 IV 为空，整段播放零 seek。

2. **两个重建同时跑 = 纯人声版被写坏**
   - 症状：预览提示「找不到视频」，控制台一片 `Invalid NAL unit size`。
   - `rebuild.sh` 用 `.rebuild.lock` 加锁（PID 还活着就 exit 3）。
   - `mkpure.py` / 成片合成必须**先写临时文件再改名**（`os.replace` / `mv -f`），
     预览正开着的时候绝不能读到半个 mp4。

3. **删除落地后要清空 `deletions.json`**（见上）。

4. **别在重建跑着的时候改 `rebuild.sh`** —— bash 边读边执行，改到一半会 `syntax error near unexpected token` 把自己读崩。

5. **「删了字幕、画面不跳」= 帧和秒混用**
   - 删除区间 `IV` 存的是**帧号**，`video.currentTime` 是**秒**，比较/skip 前必须 `Math.round(v*FPS)`。
   - 症状：总时长变短了（说明删除算进去了），但播放时画面照旧、字幕比画面超前 —— skip 判断永远为假。
   - 同一天踩了两次：一次 `skew` 累加错，一次改成按帧后忘了换算。

6. **预览页改了 js 不生效 = 被代理缓存了**
   - 这台机的浏览器走 HTTP 代理，连 `127.0.0.1` 也走；代理会把 js 缓存住，
     表现是「代码明明改了，页面还在跑老逻辑」，改一晚上都找不到原因。
   - 做法：`preview_server.mjs` 送 HTML 时，把 `<script src="xxx.js">` 改成
     `src="xxx.js?v=<该文件的修改时间>"`，版本号一变 URL 就变，代理必须回源。
   - 静态文件再补上 `Cache-Control: no-store, no-cache, must-revalidate`。

7. **「选了本段删掉，播放时本段还在」= 原片时间被当成预览时间**
   - 保存/重建用的是**原片时间**（`cuts.json` 的 `src0/src1`），供 `apply_deletions.py` 重切；
     即时预览用的是**当前预览视频时间**（`BASE.groups` 里未重映射的 `t0/t1`）。
   - 预览时不能把原片时间再套一遍 `cuts.json` 老 `out0/out1` 映射：
     如果 `cuts.json` 与当前预览视频不是同一代，画面会跳到后面另一段，
     字幕删了但用户选的那一段仍然在播。
   - 正确做法：同一份待删清单保留两套坐标 —— `s0/s1` 给重建，`pv0/pv1` 给即时预览；
     调 `setOutDels()` 直接按当前预览视频帧号计算 `IV`，调 `setDels()` 才走原片→成片映射。
   - 删除后要同时验证三件事：总时长减少、被删组文字隐藏、播放头跨过该区间时视频确实跳过。

## 19. 构建与质量检查

### 19.1 Build 校验

`build.mjs` 应至少检查：

- 时间轴数据结构。
    
- 文字长度。
    
- 字号范围。
    
- 文字宽度。
    
- 文字位置。
    
- 组间重叠。
    
- 同屏文字数量。
    
- `split` 和 `crack` 的配套关系。
    
- `crack` 字号、字数和垂直位置。
    
- 蒙版关键帧。
    
- 资源文件是否存在。
    

### 19.2 逐帧渲染

典型命令：

```
node "<skill-dir>/engine/build.mjs" --project "<项目绝对路径>"

node "<skill-dir>/engine/render_frames.mjs" --project "<项目绝对路径>" \
  --start 0 \
  --end <总时长> \
  --fps 30 \
  --out overlay \
  --force
```

渲染应支持断点续跑。

不要仅凭脚本退出码判断成功，必须检查帧文件数量和完整性。

### 19.3 四数校验

交付前必须检查：

|项目|检查标准|
|---|---|
|时长|与 `timeline.total` 一致|
|分辨率|与目标输出一致，默认竖屏 1080×1920|
|帧数|与总时长 × FPS 对应|
|音频|约 -16 至 -20 LUFS，TP 不高于 -1.5 dBTP|

帧数对不上，说明 overlay 序列和视频可能不对齐，画面会逐渐偏移。

### 19.4 抽帧 QA

至少检查：

- 每个文字组的中点。
    
- 每个组间空隙。
    
- 每个动效的入场中间帧。
    
- 每个动效的出场中间帧。
    
- 每个蒙版转场的收缩过程。
    
- 蒙版最小圆孔帧。
    
- 蒙版扩张过程。
    

每段至少抽取代表帧，整条视频建议制作约 25–37 帧的总览图，具体数量根据时长和复杂度调整。

**空隙帧也必须检查。**

主要检查：

- 上一句退场是否干净。
    
- 下一句是否提前出现。
    
- 文字是否残留。
    
- 是否出现意外黑屏。
    
- 蒙版是否遮挡大字。
    
- 动画中间帧是否出现错位。
    

### 19.5 精确抽帧

不要依赖快速 seek 来精确检查动效帧。

推荐按帧号抽取：

```
ffmpeg -v error -y \
  -i output.mp4 \
  -vf "select='eq(n\,98)+eq(n\,99)'" \
  -vsync 0 \
  qa/frame-%03d.png
```

帧号：

```
frame_number = round(time_in_seconds × fps)
```

`-ss` 放在输入前面时可能吸附到前一个关键帧，导致抽出的不是目标时点。

### 19.6 圆形蒙版检查

至少检查：

1. 收缩过程。
    
2. 最小圆孔帧。
    
3. 扩张过程。
    
4. 大字是否仍然完整可读。
    
5. 音效是否与最小圆孔帧对齐。
    

可以通过读取 overlay PNG 的 alpha，在圆心行寻找透明区域宽度，确认圆孔尺寸。

### 19.7 最终检查清单

#### 内容

- 口播稿经过人工校订。
    
- 数字、专名、英文和术语已经核对。
    
- 已清理水词、停顿、重复和口误。
    
- 删除内容没有破坏语义。
    
- 切片边界合理。
    
- 关键观点没有遗漏。
    
- 没有违规和敏感内容。
    

#### 视觉

- 已选择适合的视觉风格。
    
- 字体、颜色和人物处理一致。
    
- 大字位置根据素材测量。
    
- 文字没有遮挡人脸和重要信息。
    
- 原片字幕得到妥善处理。
    
- 同屏文字块不超过 3 个，每块不超过 2 行。
    
- 字号有层级。
    
- 重点文字有描边和投影。
    
- 跟读字幕 Y 位置有变化。
    
- 价格和结论句适当独占一屏。
    
- 文字叠印转场自然。
    
- 没有文字残留或提前出现。
    
- 画面没有显示内部风格编号或描述。
    

#### 动效

- 动效中间帧已检查。
    
- 使用 `split` 时容器宽度正常。
    
- 使用 `split` 时出场缩放作用在 `.splitwrap`。
    
- `crack` 第二句有足够可见时长。
    
- 圆形蒙版最小圆孔是主播头部大小，不是全黑。
    
- 蒙版和文字严格同帧。
    
- 转场音效与画面动作同步。
    

#### 音频

- 人声清晰。
    
- 音量适当。
    
- 音乐没有遮盖人声。
    
- 音效与动作同步。
    
- 没有爆音、削波和异常静音。
    
- 响度和 True Peak 检查通过。
    

#### 渲染与交付

- 时长正确。
    
- 分辨率正确。
    
- 帧率正确。
    
- 帧数正确。
    
- 音画同步。
    
- 成片实际播放检查。
    
- 分段切片已生成。
    
- 口播稿、打点表和时间轴已保存。
    
- 字幕文件按要求输出。
    
- 最终交付目录没有无关临时文件。
    
- 坚果云同步后核对文件数量和完整性。
    
- Codex 右侧边栏已提供动效预览。
    
- 项目目录保留 `preview.sh` 兜底。

# D. 最终执行原则

1. 内容优先于视觉效果。
    
2. 真人和真实素材优先于无关装饰。
    
3. 原片字幕优先保留，确实需要去除时改构图，不简单涂抹。
    
4. 七套风格是完整的可复用视觉体系，选定后整套执行。
    
5. 音乐、音效和字体使用本机共享资源。
    
6. 公共引擎只有一个事实源，新项目直接复用 skill，引擎和音频库都不复制。
    
7. 单集时间轴、配色和测量结果不污染公共引擎。
    
8. 能改时间轴解决的问题，不修改引擎。
    
9. 复杂效果必须通过中间帧和实际成片验证。
    
10. 交付前检查内容、画面、声音、帧数和文件完整性。
    

**最终标准：一条视频不仅要好看，还要准确、自然、可读、可复现，并且能稳定地批量生产。**
